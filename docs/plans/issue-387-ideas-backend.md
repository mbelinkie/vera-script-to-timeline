## Representation and validation

`stt-idea-outline/v1` contains exactly `schemaVersion`, a stable v2 `documentId`, and `items`. Each item contains exactly `id`, nullable `parentId`, lexical `orderKey`, exact `text`, `state: open|incorporated`, `linkedDraftBlockIds`, `collapsed`, `version`. The flat array is a canonical depth-first preorder: a parent precedes its contiguous subtree; sibling `orderKey`s are unique and strictly increasing using JavaScript code-unit ordering. Validation rejects ambiguous/noncontiguous ancestry, missing parents/cycles, duplicate IDs, repeated backlinks, unrecognized fields/types, invalid UUIDs, 0/overflow versions, and non-JSON values. Bounds: 2,000 items, 32 levels, 32,768 UTF-16 units per item text, 128 units per order key, 512 KiB serialized JSON. Keep text and line endings exact; only canonicalize UUID casing.

`checkedIdeas(input, documentId)` is a pure closed validator, and `emptyIdeasV1(documentId)` synthesizes the zero-revision view for existing projects. `promoteIdeaToNoteV1(document, outline, ideaId, blockId, orderKey, gap)` validates inputs, then uses the existing `applyRowEditV2` `create_row` command with exact `RowGapV2`. The created row is a `note_draft` with unchanged Idea text, `state:"excluded"`, `version:1`. The old Idea remains at the same parent/order/text, marked `incorporated`, with the new Draft ID appended once to its backlink list and its item version incremented. Multiple distinct deliberate promotions are allowed. `rowEditRevision` advances through the existing row-edit implementation; `liveHeadSequence`, `liveStateVector`, `liveContentHash`, and stable document IDs are preserved. No build eligibility is inferred from `incorporated`.

## Database design and migration

- Existing **001 documents, 002 comments, 003 history** migrations are immutable. The separate requested `migrations/002_stt_ideas.sql` filename is uniquely named, but its schema receipt is `stt_project_ideas_004` with version **4**, digest pinned from exact SQL bytes, distinct advisory lock `38000004`. It adds a compound project/document identity index only, never rewrites 001/002/003.
- `stt_idea_heads` is the mutable current head: `(project_id PK, document_id, revision, ideas_json TEXT, content_digest, updated_by)`. The compound FK binds it to the same-project v2 head. An absent row means synthetic empty v1 at revision **0**; the first author-authorized write inserts a revision-1 head without backfilling old projects. The head stores the **same exact text bytes** that were SHA-256 digested, not jsonb-normalized data.
- `stt_idea_revisions` has immutable append-only `(project_id, revision)` and `(project_id, actor_id, client_mutation_id)` keys, `expected_revision`, source document, operation (`put_ideas|promote_idea`), exact request/content digests and JSON, and nullable target v2 document revision/digest. Database constraints assert sequential revision/operation shape and target document existence on promotion.
- `stt_ideas_mutation_receipts` is a separate append-only replay index, keyed by project+actor+mutation ID and FK-linked to the actual Ideas revision (and optional document revision). The same mutation ID across Ideas PUT/promotion is rejected when content/operation differs. The document write path must also check this Ideas keyspace to prevent silent cross-endpoint aliasing; do not assume the two independent SQL unique indexes alone enforce it.
- Existing `stt_revision_immutable()` trigger protects both history and receipts; project/doc FKs, SHA-256 checks, positive revisions and serialized size bounds reject malformed database writes. The Ideas schema is a new forward-only migration and its deployment/QA host allowlist integration belongs to phase 4.

## Authorized service and transactional promotion (phases 2–3)

Public service inputs are **closed**. `GET ideas` returns `{projectId,ideasRevision,digest,ideas}`. `PUT ideas` accepts `{expectedIdeasRevision,clientMutationId,ideas,writeSessionId?}`. `POST promotions` accepts `{expectedIdeasRevision,expectedRevision,clientMutationId,ideaId,draftBlockId,orderKey,destination:{sectionId,afterRowId,beforeRowId},writeSessionId?}`. The server derives project and actor from the route and injected trusted identity, not from client-claimed role/tenant data. GET uses existing `view_document`; PUT/promote uses `edit_document`, rechecked in the same transaction even on replay and with caller's write session.

Use existing whole-operation SERIALIZABLE retry (only `40001`/`40P01`, bounded) from `ProjectDocumentService.transaction`. For new PUT: authorize, verify matching idempotency receipt/key, verify document ID and current Ideas digest, compare expected Ideas revision, validate version transitions relative to stored items, insert immutable Ideas revision/receipt and conditional CAS the Ideas head. New items start version 1; changed items increment by exactly 1; unchanged items keep their versions. Deletion is retained in immutable history. No current document revision is advanced by Ideas-only changes.

For a promotion: authorize and replay-check first, load and validate both heads/digests and their independent expected revisions, apply pure helper, run existing `checkedDocument`, insert the normal immutable v2 document revision plus Ideas revision/receipt, then conditionally CAS-update **both** heads in the same transaction. Any unique collision, revoked membership/session, mismatched fingerprint, stale version, failed CAS, missing source, malformed gap, invalid row or DB failure aborts the entire transaction. Retrying an identical successful request returns the original result with `duplicateDelivery` and no additional revision. Distinct requests must not use a previous `draftBlockId` or Idea ID. Return only sanitized authorization/conflict metadata; never leak source text or SQL.

## HTTP, build exclusion and verification (phases 4–5)

Add `GET /v1/projects/{id}/ideas`, `PUT /v1/projects/{id}/ideas`, `POST /v1/projects/{id}/ideas/promotions` to `packages/project-documents/src/api.ts`. Authenticate through the existing trusted `SuiteIdentityPort` **before** body parsing; preserve closed fields, JSON-only content, request streaming limit, `no-store`, 400/401/403/404/409/503 semantics and tenant boundaries. Host `migrate.ts` must explicitly allowlist the three tables and the new migration receipt/checksum while rejecting unknown tables and altered old migrations.

Focused evidence: model depth/preorder/order/identity/size/invalid-shape and exact text; migration repeat/checksum/rollback/append-only and preexisting-project lazy genesis; service role and session denial, replay under revocation, old/changed item version CAS and cross-tenant reads; promotion two independent CAS heads, intentional multiple promotions, stale heads, digest tamper and rollback after a partial attempted write, deterministic concurrent two-client race on disposable Postgres when available. Compare pre/post Ideas-only saves: exact `stt_document_heads` bytes/revision/digest, frozen build JSON and compiler events/media requirements **unchanged**. Only a deliberately promoted Draft **note** is added to v2; even that note is excluded from spoken build output. Run focused workspace checks and `VITEST_MAX_WORKERS=1 npm run validate:fast` in phase 5; never run full `validate` on the Mac. Retain synthetic verification in `docs/verification/issue-387-ideas-backend.md`, run review once per current policy, and hand off a PR including `Closes #387` for CI/merge acceptance.
