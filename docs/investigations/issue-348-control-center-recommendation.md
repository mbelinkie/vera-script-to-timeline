# #348 — VERA control center research conclusion

**Decision (2026-11-01): ADOPT GitHub Projects #2 as the queue authority, EXTEND the existing VERA Progress dashboard under #401, BUILD no additional Kanban/CI/agent control plane.**

This is a bounded research finding, not implementation, approval, dispatch, hosting, or issue closure. [#401](https://github.com/mbelinkie/vera-script-to-timeline/issues/401) alone owns the dashboard integration/rendering and first-screen experience.

## Existing infrastructure and gaps

- [GitHub Project #2](https://github.com/users/mbelinkie/projects/2) already holds Queue Order, Priority, Status, Size and project metadata. Its [table views](https://docs.github.com/en/issues/planning-and-tracking-with-projects/customizing-views-in-your-project/customizing-the-table-layout) offer grouping/filtering/sorting. **Status, label, timestamp, issue number and a workstream label cannot prove execution order, current agent activity, Producer approval, or a CI slot owner on their own.**
- On default-branch [scripts/project-progress.mjs](https://github.com/mbelinkie/vera-script-to-timeline/blob/main/scripts/project-progress.mjs), VERA still has the static HTML generator; [scripts/project-progress-lib.mjs](https://github.com/mbelinkie/vera-script-to-timeline/blob/main/scripts/project-progress-lib.mjs) uses GitHub GraphQL budget preflight. Unmerged [draft PR #395](https://github.com/mbelinkie/vera-script-to-timeline/pull/395), extracted from skipped [PR #375](https://github.com/mbelinkie/vera-script-to-timeline/pull/375), offers localhost live server, 15-minute/default + manual refresh, a shared ordered queue, dependencies, Chat review labels, and Finder launcher. **The actual running local branch/artifact must be inspected by #401** before assuming either path is deployed. Its proposed queue currently appears below KPIs/milestones: #401 owns the layout fix.
- [CI queue #361](https://github.com/mbelinkie/vera-script-to-timeline/issues/361), [docs/CI_QUEUE.md](https://github.com/mbelinkie/vera-script-to-timeline/blob/main/docs/CI_QUEUE.md), Actions and durable state on branch `vera-ci-queue-state` already enforce one **fail-stop** CI validation slot, exact PR head/base checks and post-merge main smoke. They are sources of evidence, not an invitation to install another CI scheduler.

## Smallest #401 scope, data and update design

1. **Queue above the fold:** at desktop **1366×768**, a compact page title and freshness/stale indicator, then the **queue controls and first useful rows**, before any charts, KPI cards or milestone audit. DOM reading/focus order must match. On mobile **390×844**, use compact row/card projection and preserve accessible next-action controls. Filters: Chat can advance / My approval / DeepSeek candidate or blocked / Codex ready / Waiting for CI / Blocked or stale / All.
2. **Two logical work lanes, not workstreams:** A = Chat investigation/research and Producer decision; B = implementation/integration, with bounded, ordinary non-design/non-security tickets considered **DeepSeek-first only after proper authorization**, otherwise Codex for unsuitable/escalated work. Render current **Next actor** and a concrete **Next action**, not a purported live agent count. A task can show useful Chat work and a separate Producer approval gate at once. Its review, publication hold, CI and acceptance each remain separate axes. One repository-wide CI slot across both lanes.
3. **Read-only evidence joins:** Project #2 Queue Order and native GitHub dependencies; [#378](https://github.com/mbelinkie/vera-script-to-timeline/issues/378)'s current-revision, Producer-authored `VERA_CHAT_REVIEW_V1` digest **and** `chat-reviewed` label; [#396](https://github.com/mbelinkie/vera-script-to-timeline/issues/396)/draft [PR #397](https://github.com/mbelinkie/vera-script-to-timeline/pull/397)'s distinct DeepSeek eligibility, authorization, global-off, actual run receipt and verified artifact/test results; [#399](https://github.com/mbelinkie/vera-script-to-timeline/issues/399)'s real issue-to-local Codex UUID mapping/claim; exact PR/SHA, durable #361 queue and Actions run, main smoke; Producer acceptance separately. [#398](https://github.com/mbelinkie/vera-script-to-timeline/issues/398) same-thread CI results handoff is later, **not** required for initial display.
4. **Refresh/availability:** Reuse snapshots, deliberate manual refresh and bounded periodic refresh (**#395 default 15 minutes**, subject to GraphQL budget tests), [direct rate-limit preflight/host lock](https://github.com/mbelinkie/vera-script-to-timeline/blob/main/docs/roadmap-rate-limit-investigation.md). Client-side filtering must not cause fresh GitHub API calls. No active CI poll loop, new scheduler, model calls or automatic launches. Per-source fetched time/error; keep last good snapshot **marked STALE** on failure, never show optimistic green/ready. Mac sleeping/offline: **localhost unavailable** and local old data stale; GitHub web issues/Project/Actions stay usable. Secure remotely hosted mobile dashboard is a separately authorized problem.
5. **Safe action links:** Chat link opens *interactive* draft review, not auto-approval. Codex `codex://threads/<uuid>` only when proven exact UUID exists. DeepSeek live dispatch remains OFF until authenticated explicit command + review/type/safety gates and $10 lifetime spend ledger are verified. CI links open #361/Actions, never enqueue/resume. Missing integrations show a reason, never a fake clickable launch control.

### Illustrative state model — deliberately hypothetical, not current VERA ticket claims

| Sample | Lane | Independent review, publication and CI states | Correct interpretation |
| --- | --- | --- | --- |
| A | Chat/Producer | Chat preflight done, Producer approval pending; PR *in review* while publication held **and** waiting for sole CI slot | Approval/hold remains separate from waiting CI; review ≠ publishable. |
| B | Implementation | Bounded DeepSeek candidate, no authorization receipt, global dispatch OFF; no CI yet | “Potentially eligible; dispatch unavailable,” not running/passed. |
| C | Implementation | Code candidate exact-SHA CI failed, queue **PAUSED** fail-stop with later candidates retained | Repair/explicit operator recovery; do not continue automatically. |
| D | Both | Candidate PR delivered, separate **main smoke** running/failed/unknown; acceptance pending | CI status and Producer signoff are independent. |
| E | Any | Mac asleep or source/API refresh failed | Show **STALE / unavailable / last source time**. GitHub web fallback still works. |

## Effort, risks and cheap acceptance probe

- **M0 layout** ~0.25–0.75 engineering day; **M1 truthful source joins + next-actor projections** ~1–3 days, potentially 3–5 if missing evidence APIs; **mobile responsive UI** ~0.5–2 days. These are #401 implementation estimates, **not** a #348 work order.
- **M2 safe conditional action navigation** ~1–3 days after #378/#396/#399 mechanisms actually work; no authorization to dispatch from render. **Mobile hosting/authentication**, if desired, requires a distinct security/ops estimate; no hosting provisioned.
- Biggest unknowns: actual local running dashboard branch/artifact, GraphQL page budgets and fresh snapshots, authoritative Chat approval verification, DeepSeek receipts/global disable, Codex UUID provenance, mobile remote-access requirements.
- **Cheap proof, owned by #401:** focused progress tests plus read-only local browser smoke at **1366×768** and **390×844** showing first *rows* before scrolling; synthetic review + CI wait, separate hold, paused CI failure, stale approval digest/unknown source and global DeepSeek-off, verifying no model/CI calls on render. Do not run native Resolve or consume paid model credits for UI validation.

## Discard / boundary

Discard a separate Kanban/queue database, manual duplicate status tracking, SwiftBar build, ntfy deployment, custom CI scheduler, active watcher/poller, remote-hosted dashboard, and any #348 renderer edits. Keep native GitHub notifications; revisit optional ntfy/mobile remote hosting only after a demonstrated need and separate approval.

**Research requirements satisfied by this document:** sourced open-source comparisons (license, activity, fit and limitations), adopt/extend decision, two-lane/CI/hold/stale model, data/update/side-effect plan, engineering and monthly operating estimates, baseline, and cheap validation. This is a **docs-only research deliverable for review**; its PR still needs normal review/CI/merge and Producer acceptance. Neither #348 nor #401 is automatically closed or approved by this document.
