# Checkpoint 9 plan review — whole-row narration handoff

Read-only review complete (`checkpoint-09-narration-plan.md`, the accepted `narration/service.py`, `narration/cache.py`, `narration/compiler_dependencies.py`, and the already-reviewed `compiler-core.ts` sequencing and `issue-144-semantics.ts`/`roundtrip_build.py` code from earlier checkpoints). This is a pre-implementation plan review — there is no `roundtrip_narration.py` yet, so findings below are precise requirements for the implementer to get right, not bugs in existing code.

## Is the smallest handoff correctly reusing accepted APIs?

Yes. I traced the actual mechanics rather than taking the plan's claim at face value:
- `NarrationService.process_block` (service.py:250-403) is cache-keyed entirely by `block_id`+`block_revision`+text+profile/settings hash (via `SynthesisRequest.identity`) at every layer — synthesis cache, normalization cache, and asset cache. There is zero cross-block coupling in the key scheme, so calling it for exactly one row cannot touch any other row's cached state. The plan's explicit instruction to call `process_block` directly — never `process_document` (service.py:109-125, which iterates and regenerates *every* active row) — is the right call and the one footgun worth naming precisely before code exists: using `process_document` here would regenerate every row and violate row isolation outright.
- `narration_dependency_from_asset` (compiler_dependencies.py:27-55) already produces a dict shape matching the existing per-row `NarrationDependency` entries used elsewhere in this codebase's fixtures, so splicing its output into `dependencies["narration"]` in place of the one changed row's entry is a direct, low-risk substitution — no new schema, no new dependency.
- `NarrationCache.publish`/`read` (cache.py:85-203) already enforce immutability, symlink/hardlink refusal, and atomic staged-rename-with-winner-reconciliation — exactly the safety properties this handoff needs for "retry uses the cache, no second synthesis," with no new code required to get that guarantee.

## Row-isolation and identity/cache/replay — one concrete precision risk

**Finding (the one thing most likely to go wrong, name it before code):** the plan requires checking "the same project/draft, row identity/order and narration inventory; one changed narration text... Unchanged text requires unchanged row version" before calling the provider. If this diff is implemented as a naive whole-document comparison, it will incorrectly reject a document that has already been through `applyVisualDecisions`'s composition (checkpoint 6), which unconditionally mutates `document.liveHeadSequence` (+1), `document.liveStateVector` (→ `""`), and `document.liveContentHash` (recomputed) as part of *any* accepted edit — fields that will legitimately differ between the pre-edit baseline and the document this handoff receives, with no narration change involved at all. **Minimal fix:** the "nothing else changed" check must explicitly exclude `liveHeadSequence`, `liveStateVector`, and `liveContentHash` (and any visual-event version bumps already applied in the same composition pass) from the comparison, comparing only block identity/order/text/version within `activeDraft.blocks`.

## Will it prove complete new-row synthesis without contaminating unchanged rows?

Structurally yes, for the reasons above (per-block cache keys, no `process_document` use) plus the architecture already confirmed in checkpoint 7: because visual/narration anchors are token-ID-based and the compiler lays blocks out via a running cursor (`compiler-core.ts:376-397`), an unchanged row's compiled content and local timing never need to be touched — only its *absolute* position shifts. The plan's own test list already includes the right check for this ("add an unchanged following row with a visual... block-local geometry is unchanged while its absolute start shifts"); nothing about the handoff's design works against that.

## Validation, synthetic labeling, and provider-authorization boundaries — one real gap to name precisely

- **"Validate with the actual accepted script validator"** — this is TypeScript-only; Python has no direct call into it. The only accepted, no-new-dependency mechanism is the existing compiler subprocess (`issue-144-compile-cli.ts`, already wrapped by `PreparedBuild._compile`), which validates *and* compiles in one step — exactly the "actual compiler is the authority" pattern already endorsed in checkpoints 6-8. **Recommend the plan/implementation state this explicitly** so nobody is tempted to reimplement validator logic in Python or shell out to Node in some new ad hoc way.
- **Synthetic-lane gate — the plan's intent is right, but nothing in the reused code enforces it for you.** `NarrationAudioAsset.kind` is hardcoded to `"temp_synthetic"` unconditionally inside `process_block` (service.py:335) for *every* caller, real or fake — it does not distinguish #144's injected test provider from a genuine #145 run, since even a real pre-recording synthesis is "temp_synthetic" in this model (per §8.3's own locked-audio lifecycle). So "this first segment accepts only the `synthetic_injected` lane" cannot be enforced by relying on that field; it needs its own explicit guard. **Minimal fix:** mirror the exact pattern already proven in `NativeStages.__init__` (`roundtrip_native.py`) — `if build.request["evidenceLevel"] != "synthetic_injected": raise ProofBuildError(...)` at the top of the new function, before any provider call.
- **File reading should reuse the existing strict boundary, not a new one.** The plan says "a literal revised-document file" with no new dependency; the implementer should reuse `roundtrip_build._operator_bytes`/`_parse`/`load_operator_json` (already imported by other #144 modules) rather than a bare `Path.read_text()`/`json.loads()`, to keep the symlink/duplicate-key/BOM/integer-range protections consistent across every file boundary in this harness.
- **"Refuse identical old recording bytes"** is the right defense against exactly the failure mode checkpoint 7 called out ("a manually rewritten input or merely relabeled old recording cannot substitute for integrated regeneration") — concretely, this means comparing the newly generated asset's `normalized_audio_hash` against the *prior* row's `audioHash` and refusing equality, which guards against an injected test provider (or a lazy real one) that ignores its input text and returns canned audio.
- **"Refuse failed placeholder output" and "missing word marks" require explicit checks, not inherited ones.** `narration_dependency_from_asset`/`_validate_asset` *permit* `status=="failed"` (compiler_dependencies.py:67) and permit a `"ready"` asset with only `"sentence_start"` precision (zero word marks) — neither is rejected by the existing projection. The new function must add both checks itself.

## UTF-16 offsets — name the exact mechanism before code

The plan's own check list names "UTF-16 surrogate pairs," correctly. `_map_mark`'s validation (compiler_dependencies.py:136-160) only checks that `start_utf16 < end_utf16` as integers — it trusts whatever the provider supplies. If the injected test provider computes these offsets using Python's native string indexing (codepoint-based) rather than actual UTF-16 code-unit counting, any text containing an astral character (emoji, rare CJK) will silently produce wrong offsets once consumed by the JS compiler's native UTF-16 indexing — and this would not show up in an ASCII-only fixture. **Minimal fix:** the test provider must compute `start_utf16`/`end_utf16` via UTF-16 code-unit counting (e.g. encode to `utf-16-le` and divide by 2), and the planned surrogate-pair test must actually include an astral character, not just a BMP non-ASCII one.

## Blockers

**None found.** Everything above is a precision requirement for the implementer, each independently verifiable by the test list the plan already proposes (with the one addition I'd make: ensure the surrogate-pair test uses an actual astral character, not just a non-ASCII BMP one). The bounded scope (one changed row, no rearrangement, no multi-row edits, `synthetic_injected` only) is appropriately narrow and doesn't reopen the settled whole-row policy or revisit splicing.
