## Primary finding: "bind a generation intent" may be unneeded machinery — name what gap it closes, or omit it

I worked through why `NativeStages._reserve_intent` exists at all: `run_studio_assembly`'s `create_project` call has no inherent idempotency — calling it twice creates two different native projects, so an external exclusive-reservation file is the only way to prevent a duplicate effect on retry. I then checked whether narration generation has the same problem, and it doesn't:

- `NarrationService._raw_result` (`service.py:151-193`) holds `self.cache.lock(synthesis_key)` — a *blocking* `fcntl.flock(LOCK_EX)`, not non-blocking — for the entire duration of the cache-check, provider call, and cache publish, as one atomic critical section. A second concurrent caller for the same content blocks until the first finishes, then hits the now-populated cache. This already prevents a duplicate provider call under true concurrency, not just sequential retry.
- `ProofSession.run()`'s own `proof.lock` already serializes every `session.run(action)` call globally (non-blocking, immediate refusal on contention) — so two concurrent `generate-omission` calls, even for different decision keys, can't both be in flight at the session level in the first place.
- The durable handoff file itself, once written via `publish_immutable_output`, is already the record that "generation for this decision succeeded" — and the plan's own requirement to re-run `replace_row_narration` fresh before every `finalize-omission` call (not skip it) means replay safety comes from re-invoking an idempotent, cache-backed function, not from checking an intent marker first.

This is structurally the same situation as the compile step, which also has no separate intent file — compilation is pure and cache-irrelevant-but-idempotent, so the existing job-store lease/epoch mechanism is sufficient. Narration generation is the same shape (pure input → cache-deduplicated output), not the native-create shape (no idempotency of its own). **Before implementing a separate generation-intent reservation file, name the specific gap it closes that the cache lock + proof lock + durable handoff file don't already close — if none exists, omit it.** This directly matches the "unneeded machinery" concern already raised and addressed in checkpoint 12e's own review.

## Shared `_decision`/`_promote` dispatch — the plan correctly anticipates branching, not naive reuse

I checked `_decision()`'s current hardcoded check `receipt.get("status") != "revised"` (`roundtrip_proof.py`) against the omission decision's actual status value, `"prepared_revision"` (confirmed in checkpoint 12e's `decision_receipt`). A naive shared `_decision()` would reject every omission decision outright on this string mismatch alone. The plan already states "the original visual path remains strict" and requires teaching `_decision` to dispatch — so this isn't a gap I'm discovering, it's a correctly-anticipated requirement. The concrete minimum: `_decision` needs to branch on the receipt's schema (`issue-144-decision/v1`-style vs `issue-144-omission-decision/v1`) before checking status, and the omission branch's rebuild path needs its own freshness check using `OmissionProof`'s split-capable capture validator rather than `_occurrence_identity` — which the plan explicitly preserves as "the visual branch keeps its exact birth UID gate." Confirmed consistent with everything already proven about keeping these two identity gates structurally separate (checkpoint 12d).

## Materialization map construction — correctly reuses an established pattern, not a new mechanism

The "for every unchanged non-placeholder source, reuse its verified origin/artifact/policy; the one new narration source matches the just-verified replacement; placeholders stay the package stage's job" sequence is exactly the pattern already demonstrated in the checkpoint-9 and checkpoint-12c test fixtures' own materialization-plan construction loops (`if source["id"] in old: plan[source["id"]] = old[source["id"]] else: ...`, skipping `kind == "placeholder"`). This isn't new design, it's promoting an already-proven test pattern into production code. The "refuse new unexplained sources" requirement is largely already guaranteed structurally by `finalize-omission`'s existing `withoutNarration(dependencies) == withoutNarration(prior)` check (checkpoint 12c) — the compiled preview's source list can't gain an unexplained entry without a non-narration dependency change that `finalize-omission` already refuses. Treating this as defense-in-depth at the materialization layer rather than the sole safeguard is appropriate.

## Historical constructor discipline — correctly extends an already-proven pattern

"An original accepted decision's historical constructor remains read-only... cannot authorize a missing generation or new native effect against an obsolete pointer" is the same shape as `OmissionProof.__init__`'s `baseline_hash` parameter already reviewed in checkpoint 12e: `self.retained = baseline_hash is not None` skips only the current-pointer-match requirement, never the full re-verification of whatever baseline is specified. Extending this same discipline to the generation/rebuild layer is consistent, not a new risk — provided the extension is literally the same pattern (skip the "is this current" check, never skip the "is this valid" check) rather than a new one.

## Everything else checked against existing mechanics — consistent

The crash-recovery requirement ("a crash after pointer publication but before the promotion receipt must recover the same verified new baseline without another advance or provider call") matches `_promote`'s already-traced logic (checkpoint 12: `if load_operator_json(self.pointer) != expected: ... else skip re-advance`). "Do not duplicate its synthesis-key algorithm" is already how `roundtrip_narration.py` behaves today — it never pre-computes the cache key, it calls `service.process_block` and inspects the returned asset afterward. No blocker found in any of these.

## Verdict

One concrete, actionable design question before implementation: justify or drop the separate generation-intent reservation file. Everything else in the plan is either a correct, already-anticipated extension of a proven pattern or a direct promotion of an already-tested fixture pattern into production code. No blocker that would prevent proceeding to wiring, conditional on resolving the intent-file question above. This does not close #144, does not substitute for composition/WI/runbook work, and does not claim real #145 qualification.
