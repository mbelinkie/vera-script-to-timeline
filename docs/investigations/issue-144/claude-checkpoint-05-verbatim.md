## 1. Concurrency / intent reservation / crash recovery — traced and confirmed safe

I traced the full lifecycle rather than trusting the tests:
- `_reserve_intent` (`roundtrip_native.py:278-299`) uses `O_CREAT|O_EXCL|O_NOFOLLOW`, flushes, `fsync`s the file and its directory before any native call — a genuine single-owner reservation; the second concurrent caller gets `FileExistsError` → `UncertainResult`, confirmed by direct trace of `test_exclusive_intent_reservation_has_exactly_one_owner`, not just its assertions.
- On a `create_project` failure *after* the side effect occurred (`lost_response=True`), `run_studio_assembly` catches the exception internally and returns a `"mutation_failed"` result (`studio_assembly.py:191-203`) rather than raising — `NativeStages.execute` still publishes that result immutably, then `_result()` rejects anything not literally `status=="verified"`, raising `UncertainResult`. Since `intent_path` already exists on any retry, the `if context.stage=="building_resolve_timeline" and not intent_path.exists()` guard (`roundtrip_native.py:244-246`) permanently blocks a second `create_project` call. Traced through `build_jobs.py`'s `_claim`/`run_one`/`_stop_attempt`: `UncertainResult` maps to job status `"waiting"`, not `"failed"` or `"complete"`, and no new lease/attempt can re-enter the mutating branch. **No duplicate-effect path found.**
- Two inspections per native stage (once inside `execute()`, once more when `build_jobs.py:685-726`'s `run_one` calls `reconcile()` again to confirm after `execute()` returns) plus the same again on `verifying_timeline`, plus full re-inspection on every subsequent `build.run()` replay via `PreparedBuild.run()`'s explicit adapter-replay loop (`roundtrip_build.py:516-535`) — confirms "completed replay performs fresh read-only inspection" is real, not just claimed.

**Finding (Low, cosmetic, `roundtrip_native.py:216-236`):** `reconcile()` only raises `UncertainResult` directly when `intent_path.exists() and not result_path.exists()`. When intent *and* a non-"verified" result both already exist (the post-`mutation_failed` replay case), it falls through to `return False` instead, deferring the same conclusion to the next `execute()` call, which re-derives it via `_result()`. No safety impact — confirmed no new native call happens on that path — but `reconcile()` could short-circuit this case directly for one fewer round trip. Not worth doing before anything else.

## 3. Inspector contract vs. the real accepted boundary — material overclaim found

This is the substantive finding the prompt asked me to surface before WI work begins.

**Finding (High, `roundtrip_native.py:118-136` vs. `studio_spike.py:637-677` and `contracts/timeline-manifest-v1.schema.json:487-534`):** the inspector contract requires each observed item's `event` field to equal the compiled manifest's `TimelineEvent` object **exactly**, including `id`, `sourceId`, `provenance` (`documentId`/`blockId`/`authoringKind`/`authoringId`), `alignmentVersion`, and `timingPrecision`. But the only accepted write path into native state, `place_events` (`studio_spike.py:637-677`), hands Resolve's `AppendToTimeline` nothing but `startFrame`/`endFrame`/`mediaType`/`trackIndex`/`recordFrame` — it never persists `id`, `sourceId`, `provenance`, `alignmentVersion`, or `timingPrecision` anywhere in native state, and there is no per-clip custom-data write path analogous to `add_marker`'s `custom_data` (that mechanism exists only for markers). **A real inspector has no native-observable way to recover those fields**, so the exact-equality check as specified is unsatisfiable by any real implementation, not just unimplemented. The test fake sidesteps this honestly but completely — `"event": copy.deepcopy(event)` (`tests/test_issue144_native_build.py:121`) literally echoes the expected value rather than deriving anything, so this exact-equality contract has never actually been exercised against a plausible native read.

Smallest bounded fix: before building any real WI inspector, narrow the comparison to the native-observable subset (`recordRange`, `sourceRange`, `trackId`/`trackKind`, `enabled`, `speed`, source identity resolved via `mediaUid`) and drop the requirement that non-native fields (`id`, `provenance`, `alignmentVersion`, `timingPrecision`) round-trip through native state at all — or, if exact per-event identity is genuinely required, treat adding a persisted per-clip write-back (extending the existing marker-custom-data pattern) as new, separately-reviewed scope rather than an assumed capability.

**Finding (High, `roundtrip_native.py:70-174`):** separately, `projectUid`/`timelineUid`/`itemUid`/`mediaUid` are load-bearing for the whole identity/UID-map design (and for the plan's own "read-only rehydration verifies target UID" language at `issue-144-roundtrip-harness.md:250`), but no method resembling `GetUniqueId()` (or any ID-returning call on Project/Timeline/TimelineItem/MediaPoolItem) appears anywhere in `studio_spike.py`'s verified-callable preflight surface. I'm flagging this with the same discipline the Producer asked me to apply to the project-manager folder APIs last checkpoint: I am *not* asserting this API doesn't exist in Resolve generally — I'm stating that nothing in this accepted codebase has verified it, so the inspector contract's dependence on it is currently an **unverified assumption**, not a confirmed capability. Smallest fix: before any real WI inspector is attempted, add and verify the specific ID-returning calls to `studio_spike.py`'s preflight (the same pattern already used for `GetSetting`/`GetMediaPool`/etc.), or explicitly scope the real seam to whatever identity scheme those calls actually support.

Both findings are about the *next* unimplemented segment, not a defect in what's built now — this segment's own fake inspector is honestly labeled as fabricated throughout.

## 4. Custom reconciliation vs. #35's own integrity check

**Finding (Medium, `roundtrip_build.py:516-535`):** `PreparedBuild.run()`'s adapter-replay verification loop builds each `StageContext.output_path` from `Path(stage["path"])` — the raw string stored in SQLite via `self.store.status(...)` (`build_jobs.py:309-341`, a plain read with no integrity check). This differs from `BuildJobStore.run_one()` (`build_jobs.py:685-726`), which calls `_verify_completed()` *first* — independently recomputing each stage's canonical path via `self._output_path(job_id, stage)` and comparing it against the stored row before trusting it (`build_jobs.py:385-401`). The custom loop skips that cross-check: if a `stages.path` row were corrupted or tampered to point elsewhere, this loop would run a full `adapter.reconcile()` pass — including, for the native stages, a real inspection call — against whatever is at that unverified path, before the subsequent `store.run_one()` call's own `_verify_completed()` finally catches the mismatch and fails the job. The end state is still correct (failed, not falsely "complete"), so this is not a path to a false positive, but it is one extra unguarded reconciliation pass against unverified data. Smallest fix: derive the replay loop's `output_path` the same way `run_one` does (via the canonical path derivation) instead of trusting the SQLite-reported string, or call the equivalent of `_verify_completed()` before the loop runs.
