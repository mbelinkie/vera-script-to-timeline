# Checkpoint 11 plan review — canonical row omission transformation

Read-only review complete, bounded to the listed plan, the main plan's text/row policy section, the generated contract interfaces, and the validator's affinity-resolution code. No checkpoint-11 code exists yet.

## Entity-kind inventory — confirmed complete, grounded in the actual contract

I checked `generated/contracts.ts` directly rather than trusting the plan's list. Exactly four entity kinds carry a `TextAnchorRange`: `HostVisibilitySpan`, `VisualEvent` (appearing both inside `NarrationBlock.visualEvents[]` and inside the standalone `VisualBlock.event`), `NarrationAnnotation`, and `PerformanceBeat`. The plan's "visual events, host visibility spans, annotations and performance beats, including standalone VisualBlock.event" names exactly these, with no fifth kind and no omission. `NarrationBlock.notes: string[]` carries no anchor at all, which matches the plan's explicit refusal to touch notes via any generic/recursive mechanism — confirmed appropriately conservative, not a gap.

## Affinity semantics — confirmed, not ambiguous

I read the validator's actual resolution code (`script-validator.ts:623-625`): `start = startTokenIndex + (startAffinity === "after" ? 1 : 0)`, `end = endTokenIndex + (endAffinity === "after" ? 1 : 0)`, producing a half-open token-index interval. Since this addressing is by **token ID**, not by offset, it's naturally robust to interior deletion: any anchor whose `startTokenId`/`endTokenId` survives the omission remains resolvable in the edited token array regardless of affinity, and its `quotedText` simply needs recomputing against the new array — exactly the "ranges enclosing the phrase retain endpoints and receive new quoted text/version" rule, which is the same mechanism already implemented and tested for the visual move/trim case in `issue-144-semantics.ts`. The only genuinely ambiguous case — an endpoint token ID that is itself among the removed tokens — is exactly the case the plan says must refuse rather than guess a replacement. I don't find a remaining ambiguity here.

## One concrete implementation caution (not a blocker)

The plan correctly notes the UTF-16 delta must use JS's native length, not code-point or UTF-8 byte count. Worth stating precisely for the implementer: native JS string `.length`/`.slice()` already count UTF-16 code units for free (unlike the Python side in checkpoint 9, which needed explicit `utf-16-le` encoding) — so the risk here is the *opposite* of checkpoint 9's: accidentally reaching for a code-point-iterating construct (`for...of` a string, spread `[...text]`, `Array.from(text)`) when computing the offset delta for an astral-character span, which would silently undercount by one per astral character. The ASCII-whitespace-in-gap check is safe either way it's iterated (no ASCII whitespace character is ever part of a surrogate pair), so this caution applies specifically to the offset-delta arithmetic, not the gap-content check. This is exactly why the plan's own test list already includes "UTF-16 astral values before/after the cut" — that test is the right one to catch this specific mistake.

## One concrete test-coverage recommendation

I checked whether the validator enforces any relationship between a standalone `VisualBlock.version` and its own `event.version` — it treats `block.event` as an ordinary `visual_event` occurrence (`script-validator.ts:286-292`) with no cross-check against the wrapper's own version field anywhere I could find. That means "the wrapper bumps only if its owned event changes" is a convention the new transformer must uphold entirely on its own — the validator provides no safety net for it. **Recommend one explicit test** asserting this directly: a standalone `VisualBlock` whose event is unaffected by the omission must have an identical `version` before/after, distinct from the generic "untouched entities remain identical" check, since this is the one invariant nothing downstream will catch if it's violated.

## Integration boundary — correctly identified, correctly deferred, not a blocker

I verified this against checkpoint 9's actual code rather than taking the plan's claim at face value: `replace_row_narration`'s per-block loop (`roundtrip_narration.py`) does `if row["type"] != "narration": if row != old: raise ProofBuildError("non-narration row changed")`. So if checkpoint 11's transformer does its stated job — updating a standalone `VisualBlock.event`'s `quotedText`/version when it's anchored to the edited row — the resulting document would be refused outright by checkpoint 9's existing guard, which treats *any* change to a non-narration row as disqualifying, full stop. The plan's "integration follow-up" paragraph names this exact collision precisely and correctly defers the fix to a separate, later "bounded accepted-decision handoff that permits only the actual canonical visual changes," rather than either loosening checkpoint 9's guard now or silently dropping standalone-visual support from checkpoint 11. That's the right call — loosening checkpoint 9's input guard now, before there's an explicit accepted-decision mechanism to bound *what kind* of non-narration change is legitimate, would be exactly the "arbitrary loosening" the prompt warns against. This is a correctly-named dependency, not a design gap in checkpoint 11 itself.

## Validator-only (not full compile) scoping — confirmed correct, and worth stating why

The plan says run only `validateScriptDocument`, not `compileTimeline`, as this function's final gate — unlike checkpoint 6's visual-semantics module, which does call the full compiler as its final check. I confirmed why this difference is correct rather than inconsistent: a visual move/trim never invalidates narration audio, so compiling immediately against the existing dependencies is sound. An omission *always* invalidates the row's narration dependency (stale `textHash`/`audioHash` against the new text), so attempting to compile at this stage would spuriously fail against dependencies that haven't been regenerated yet — compiling must wait until the whole-row handoff produces a fresh dependency. The plan states this reasoning explicitly ("do not compile against stale narration text/version/audio"); I'd just flag it as worth keeping in the eventual code comments, since a future reader comparing this module to `issue-144-semantics.ts` might otherwise "fix" the asymmetry by adding a premature compile call.

## Verdict

No actionable design blockers or ambiguities found. This is a minimal, coherent plan that correctly reuses the validator/serializer, correctly scopes its own entity inventory against the actual contract, correctly identifies (without attempting to solve) the one real integration collision with checkpoint 9, and correctly declines to compile against stale dependencies. The two additions I'd make are both tests, not design changes: an explicit standalone-wrapper-version-untouched assertion, and confirming the astral-character test specifically exercises the offset-delta arithmetic rather than just round-tripping unchanged astral text.

Static advisory review only — not test execution or native acceptance.
