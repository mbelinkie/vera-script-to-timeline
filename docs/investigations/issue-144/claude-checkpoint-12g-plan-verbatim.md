# Checkpoint 12g plan review — one combined three-edit proof

Read-only review complete. I'm treating the three items below as the load-bearing requirements for this plan — precise enough that getting them wrong would be a real blocker, phrased as requirements to satisfy during implementation rather than defects in the plan text itself, since no code exists yet.

## Requirements that must hold (name these precisely before writing code)

**1. The "expected auxiliary route geometry" must come exclusively from the compiler, never from any operator-suppliable file.** The plan says this value is "host-derived... bound in its report," and that's the right call — but I want to state precisely *why* it must stay that way. Checkpoint 10/12a's `primary_source_id` fix exists specifically because allowing `profile.json` (an injected-supplier-controlled file) to influence which source qualifies reopened exactly this risk. The auxiliary-route geometry proposed here is structurally different *only if* it's derived from `applyVisualDecisions`'s own recompiled manifest — never read from `profile.json` or any other file the synthetic supplier writes. If this gets implemented by passing the expected geometry through a file the supplier also touches, it recreates the already-fixed vulnerability class under a new name. This needs to be a parameter computed by the proof session from the actual compiler output and passed directly into the audio verifier call, not something staged through evidence files.

**2. Keep the auxiliary-geometry allowance structurally separate from the primary token-support decomposition.** `verify_omission_evidence`'s decomposition loop (`roundtrip_audio.py`) currently scopes `omittedTokenIds`/`decomposition` exclusively to `source["id"] == selected["id"]`. The plan's own invariant — "an explicitly verified auxiliary source trim may remove auxiliary content; that removal must never become narration deletion" — depends entirely on the new auxiliary-route-geometry-change allowance being checked as a separate structural comparison (does this route's new geometry equal the compiler-derived expected value?) and never fed into the `intersections()`/support-decomposition calculations that exist only for the primary narration source. This is the one place composing these two concerns carelessly could silently weaken the full-support-excision guarantee that's been the center of this whole audio-evidence effort since checkpoint 3.

**3. The derived visual projection must stay in-memory, never written to disk.** The plan correctly says the projection "is not native readback and must never satisfy capture, audible-evidence or fresh-target verification," but doesn't say whether it's persisted. I'd make this explicit: there's no reason to write this projection to a file at all — it's only needed transiently to feed `proposeVisuals`/`applyVisualDecisions` within the same function call that already holds the raw capture. Not persisting it removes any possibility of it later being misread by `_occurrence_identity`, `OmissionProof.audio()`, or `evidence_files` as a genuine observation, which is a stronger guarantee than relying on careful labeling of a file that exists.

## Non-blocking confirmations

**Sequencing of omission-then-visual-transfer is sound, and the plan correctly anticipates the retiming consequence.** Applying `applyAcceptedOmission` first, then transferring the two already-accepted visual ranges onto surviving token IDs (recomputing only `quotedText`, not geometry) works because `TextAnchorRange` addressing is token-ID-based, not offset-based — confirmed in checkpoint 11's trace of the validator's affinity resolution. The plan is also right that the *final* compiled geometry for the move/trim visuals will differ from what was originally observed, since the whole row's new timing marks change everything downstream — "the old edited timeline geometry establishes intent; it is not the new pacing authority" is the correct framing, consistent with the already-proven rebuild behavior from checkpoint 12f.

**All-or-nothing decision format is sufficient for #144, not a coverage reduction.** #144's original scope requires each edit *kind* individually proven (already done, separately, across the visual and omission lanes) plus proof that composing them into one revision works. A successful "all three accepted" case already exercises the hardest interaction (every transfer, every retiming dependency, at once); a mixed case would be a strict subset of the same mechanism, not a different code path needing separate proof. The schema shape itself (one `choice` field for the whole bundle) makes "mixed choices refused" structural rather than something requiring extra validation logic — consistent with `OmissionProof.choice()`'s existing shape-check pattern. I'd still recommend one explicit sentence to the producer confirming this is deliberately narrower than what #148/#145's eventual real-input, partial-acceptance workflow will need — not because it's insufficient for *this* proof, but so nobody later assumes this all-or-nothing behavior was meant to generalize.

**Fixture arithmetic checks out.** Move: [75,125)→[100,150), same 50-frame duration, +25 shift. Trim: [150,200)→[150,175), start unchanged, -25 duration — both exactly matching the hardcoded `+25`/`-25` detection in `issue-144-semantics.ts` reviewed in checkpoint 6, not an approximation.
